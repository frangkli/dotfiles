A reusable visual explanation

A worked example of the skill’s style. The flow below describes how a page gets from the agent to its reader; it is not a performance experiment.

Recommendation: save each explanation as one self-contained HTML file in the repo’s docs/plans or docs/research, and commit it with the work. When a plans hub serves the repo, it shows the page as soon as it is saved. Use the local preview for a quick look.

Read on the hub

The hub lists the page under its repo and branch once the file is saved. Its styles and controls are inside the file; no font server, chart CDN, or application build is needed.

Two useful choices

Choose based on how many explanations the reader needs to navigate.
Option When it helps Tradeoff
One standalone page
Default		 Review a plan, compare experiments, or explain a request flow. Simple to keep and share. No overview of other pages.
Pages plus a small index Navigate a related set of plans, decisions, and implementation notes. Links and page status need to stay accurate. The hub already lists every page.

What this design supports

Separating documents from the skill removes a lifecycle dependency: installing a new version of the skill need not touch existing explanations. Committing the page keeps it next to the work it explains, and git holds its earlier revisions.

The hub is reachable only where the box is. A page that has to travel is still one file that opens anywhere, with no server.

Implementation and verification details
  • The starter uses inline CSS and JavaScript, local fonts, native expandable sections, and semantic HTML.
  • The preview helper binds to 127.0.0.1 on an available port and serves only the selected file. It does not expose the enclosing project directory.
  • Check every claim against its source before finishing, then the rendered page and each control. In a research explanation, attach sources, measurement dates, and sample sizes to the actual claims. Keep examples labelled as examples.
  • Keep current conclusions separate from chronological logs. A status update should revise the recommendation when the evidence changes.
